# compositions/app

Installs the Autoheal chart into the cluster that an infra composition
(`compositions/azure` or `compositions/aws`) built. One `helm_release`, two
values documents:

1. `infra_values`: the infra composition's `autoheal_values` output (what
   Terraform built: hosts, vault, identities, database, object store, reserved
   addresses).
2. `customer_values`: the customer's `values-customer.yaml` (features, sizing,
   SSO, overrides of the suggestions).

They are passed in that order, the same as
`helm upgrade --install ... -f values-infra.yaml -f values-customer.yaml`, so a
Terraform install and a Helm or Flux install of the same files render the same
manifests. The release is `atomic` with `wait` and a 1200 second timeout: a
failed upgrade rolls back on its own.

This is the only composition with the `helm` and `kubernetes` providers. Keeping
them out of the cloud compositions means the cluster does not have to exist when
the infra folder is planned.

## Logging in to the cluster

No kubeconfig and no credential pass through Terraform. Both providers run an
exec plugin that fetches a short lived token, chosen from `cluster.cloud`:

| cloud | command | needs on the PATH |
|-------|---------|-------------------|
| `azure` | `kubelogin get-token --login <kubelogin_login_mode> --server-id 6dae42f8-4368-4678-94ff-3960e28e3630` | `kubelogin`, and `az` for the default `azurecli` mode |
| `aws` | `aws eks get-token --cluster-name <name> --region <region>` | `aws` |

On AKS the identity running the apply needs a Kubernetes role on the cluster,
for example Azure Kubernetes Service RBAC Cluster Admin. When
`compositions/azure` creates the cluster it grants that role to the deployer, or
lists it in `required_role_assignments` with `create_role_assignments = false`.
On a brought cluster, get the role from the cluster's owner
(`required_cluster_owner_actions`).

A namespace-only install works too, for a cluster owner who gives the deployer
one namespace and nothing else. The owner creates the namespace and grants
Azure Kubernetes Service RBAC Admin scoped to it
(`<cluster ID>/namespaces/autoheal`); set `create_namespace = false`. RBAC
Writer is not enough: the chart creates Roles and RoleBindings in its
namespace. The chart creates no CRDs, ClusterRoles or other cluster-scoped
objects, so it needs no more than that. See `examples/azure/split/app`.

## AWS Load Balancer Controller

In loadbalancer mode on EKS the chart binds the proxy Service to the edge NLB
target groups that `compositions/aws` made, with `TargetGroupBinding` objects. The AWS Load
Balancer Controller registers the pod IPs in them. With
`aws_load_balancer_controller = { enabled = true }` this composition installs it
first, in `kube-system`, as service account `aws-load-balancer-controller` (the
one `compositions/aws` federates when `create_load_balancer_controller_role` is
on):

- `clusterName`, `region` and `vpcId` come from `cluster`, so the pods never
  read instance metadata (the nodes allow one hop only).
- 2 replicas with a PodDisruptionBudget.
- No IngressClass, no Service mutating webhook, no WAF or Shield. The controller
  serves `TargetGroupBinding` only, which is all its role allows.
- `values` is a YAML document merged over these settings. In a VPC without a
  NAT gateway, point `image.repository` at the regional ECR copy, for example
  `602401143452.dkr.ecr.us-west-2.amazonaws.com/amazon/aws-load-balancer-controller`
  (the account differs in some regions).

The Autoheal release depends on it: the CRD and its webhook are up before the
chart installs, and on destroy the controller outlives the bindings so their
finalizers are removed. Leave it off on a cluster that already runs a
controller; that controller's role must allow `RegisterTargets` and
`DeregisterTargets` on the target groups. Ignored on AKS.

## Where the chart comes from

`chart_repository` defaults to `oci://public.ecr.aws/e4h3h0d9/charts`, and the
chart is `autoheal` at `chart_version`. An `https://` chart repository works the
same way. Any other value is read as a local path to a chart directory or a
packaged `.tgz`, used as it is (its `Chart.yaml` carries the version). The local
form is for testing a chart that is not published.

## State backend

There is no `backend.tf` here: the same composition runs on Azure and AWS, so
the backend block is generated by the caller. The Terragrunt `root.hcl` in
`examples/azure` and `examples/aws` writes `backend.tf` with `generate`. Callers that do not use
Terragrunt add their own `backend.tf` next to these files.

## Usage

See `examples/azure/prod/app/terragrunt.hcl` and
`examples/aws/prod/app/terragrunt.hcl`. The `dependency "infra"` block
reads `autoheal_values` and `cluster` from the infra folder:

```hcl
inputs = {
  cluster         = dependency.infra.outputs.cluster
  infra_values    = dependency.infra.outputs.autoheal_values
  customer_values = file("values-customer.yaml")
  chart_version   = local.v.chart_version
}
```

For an AKS cluster you bring, `compositions/azure` does not read the cluster,
so its `cluster` output has no endpoint or CA certificate. Take `cluster` from
`compositions/azure-cluster` instead, as `examples/azure/split/app` does.

## Inputs

| Name | Type | Default | Description |
|------|------|---------|-------------|
| `cluster` | object | required | The infra composition's `cluster` output, or `compositions/azure-cluster`'s for an AKS cluster you bring: `cloud` (azure or aws), `name`, `endpoint`, base64 `ca_certificate`, and `resource_group` (Azure) or `region` (required) and `vpc_id` (AWS). |
| `infra_values` | any | required | The infra composition's `autoheal_values` output. |
| `customer_values` | string | `""` | Contents of `values-customer.yaml`. Merged after `infra_values`. |
| `chart_version` | string | required | Chart version, e.g. `1.0.0`. |
| `chart_repository` | string | `oci://public.ecr.aws/e4h3h0d9/charts` | OCI or HTTPS chart repository, or a local chart path. |
| `namespace` | string | `autoheal` | Namespace for the release, created when missing unless `create_namespace = false`. Must match `service_accounts.namespace` in the infra folder. |
| `create_namespace` | bool | `true` | Create the namespace when missing. Set `false` when the deployer has rights in that namespace only. |
| `release_name` | string | `autoheal` | Helm release name. |
| `kubelogin_login_mode` | string | `azurecli` | `kubelogin --login` mode on AKS: `azurecli`, `workloadidentity`, `spn`, `msi`, `devicecode` or `interactive`. Ignored on AWS. |
| `timeout` | number | `1200` | Seconds Helm waits for the release before it rolls back. |
| `aws_load_balancer_controller` | object | `{}` | `enabled` (false), `chart_version` (`3.6.0`), `repository` (`https://aws.github.io/eks-charts`) and `values` (YAML merged last). EKS only. |

## Outputs

| Name | Description |
|------|-------------|
| `release_name` | Helm release name. |
| `namespace` | Namespace of the release. |
| `chart_version` | Chart version Helm installed. |
| `revision` | Helm release revision; increases by one on every upgrade. |

## Tests

```bash
terraform init -backend=false
terraform test
```

`tests/app.tftest.hcl` plans against mocked `helm` and `kubernetes` providers:
the login command per cloud, OCI, HTTPS and local charts, the values order, a
namespace-only install, the AWS Load Balancer Controller release, and the input
checks.
